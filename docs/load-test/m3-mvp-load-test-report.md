## 1. baseline (10 VU, 1분)

```
총 요청 수: 1672
RPS (평균): 27.60
지연 시간: avg=299.5ms / p95=428.3ms / p99=488.0ms / max=678.5ms
네트워크 레벨 실패율: 0.00%
발급 성공(201): 1671건 (99.94%)
```

Grafana에서 관찰된 점:
- **HPA가 이미 반응함**: replicas가 2 → 3으로 순간 증가 (CPU 사용률이 requests 대비 76~84%까지 튐). CPU request가 100m로 낮게 잡혀 있어, "소규모 트래픽"이라는 baseline 의도와 달리 완전한 단일 파드 상태는 아니었다.
- DB 락 대기 세션(`tuple`) 최대 8건, 커넥션 수 최대 17건 — 10 VU 수준에서도 이미 락 경합이 감지됨.

## 2. spike (3,000 VU, 각 1회 요청)

```
총 요청 수: 3001
RPS (평균): 49.58
지연 시간: avg=44042.1ms / p95=59804.4ms / p99=59822.7ms / max=59833.5ms
네트워크 레벨 실패율: 45.12% (1354건, k6 기본 요청 타임아웃 60초 초과)
발급 성공(201): 1646건 (54.85%) / 재고소진(400): 0건 / 중복(409): 0건
```

재고(`COUPON_QUANTITY=100000`)는 소진되지 않았고 중복 발급도 없었다 — 실패는 전부 "60초 안에 응답을 못 받음"이었다.

Grafana에서 관찰된 점 (테스트 구간 기준):

| 지표 | 값 | 비고 |
|---|---|---|
| 최대 replicas | 3 | HPA `min=2 max=10` 중 3까지만 확장 |
| 최대 CPU 사용률 | 72% | baseline 대비 크게 높지 않음 — CPU 바운드가 아님 |
| 최대 커넥션 수 | 22 | `max_connections=300`의 7% — 커넥션 풀 고갈 아님 |
| 커넥션 사용률 | 0.667% | 여유 있음 |
| **최대 락 대기 세션(tuple)** | **17~19** | 커넥션 22개 중 거의 전부가 같은 쿠폰 row 락을 기다리며 대기, 3분간 플래토 지속 |
| 최대 커밋 TPS | 30.6 ops/s | **baseline의 최대 커밋 TPS(30.9 ops/s)와 거의 동일** |

**결론**: VU를 10 → 3,000(300배)으로 올렸는데도 실제 처리량(커밋 TPS)은 baseline과 거의 그대로였다. 커넥션 풀과 DB CPU는 모두 여유가 있었던 반면, 커넥션의 대다수가 같은 row의 `SELECT ... FOR UPDATE` 락을 기다리며 멈춰 있었다. 즉 **처리량 상한을 만드는 건 커넥션 풀도 DB CPU도 아니라 비관적 락(행 락) 자체의 직렬화**다. 3,000명이 동시에 몰리면 절반 가까이가 락 대기열 뒤에서 응답을 못 받고 타임아웃된다.

**주의 — Grafana 히스토그램 P95/P99와의 괴리**: 대시보드 요약 타일의 "최대 P95/P99 지연"은 10s로 표시되지만, k6가 직접 측정한 값은 p95=59.8s, p99=59.8s다. `/metrics`의 지연 히스토그램 버킷이 100~500ms 구간 해상도에 맞춰져 있어 그보다 훨씬 큰 값(수십 초)에 대한 버킷이 없고, `histogram_quantile`이 가장 큰 유한 버킷 상한으로 뭉개 추정한 것으로 보인다. 이런 극단적 지연 시나리오에서는 **Grafana 수치보다 k6가 직접 측정한 값을 신뢰**해야 한다. 필요하면 추후 히스토그램 버킷에 수십 초대 구간을 추가하는 것을 고려할 수 있다.
