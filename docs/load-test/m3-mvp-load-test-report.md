## 1. baseline (10 VU, 1분)

```
총 요청 수: 1672
RPS (평균): 27.60
지연 시간: avg=299.5ms / p95=428.3ms / p99=488.0ms / max=678.5ms
네트워크 레벨 실패율: 0.00%
발급 성공(201): 1671건 (99.94%)
```

Grafana에서 관찰된 점:
- **HPA가 이미 반응함**: replicas가 2 → 3으로 순간 증가 (CPU 사용률이 requests 대비 76~84%까지 튐). CPU request가 100m로 낮게 잡혀 있어, "소규모 트래픽"이라는 baseline 의도와 달리 완전한 단일 파드 상태는 아니었다.
- DB 락 대기 세션(`tuple`) 최대 8건, 커넥션 수 최대 17건 — 10 VU 수준에서도 이미 락 경합이 감지됨.

## 2. spike (3,000 VU, 각 1회 요청)

```
총 요청 수: 3001
RPS (평균): 49.58
지연 시간: avg=44042.1ms / p95=59804.4ms / p99=59822.7ms / max=59833.5ms
네트워크 레벨 실패율: 45.12% (1354건, k6 기본 요청 타임아웃 60초 초과)
발급 성공(201): 1646건 (54.85%) / 재고소진(400): 0건 / 중복(409): 0건
```

재고(`COUPON_QUANTITY=100000`)는 소진되지 않았고 중복 발급도 없었다 — 실패는 전부 "60초 안에 응답을 못 받음"이었다.

Grafana에서 관찰된 점 (테스트 구간 기준):

| 지표 | 값 | 비고 |
|---|---|---|
| 최대 replicas | 3 | HPA `min=2 max=10` 중 3까지만 확장 |
| 최대 CPU 사용률 | 72% | baseline 대비 크게 높지 않음 — CPU 바운드가 아님 |
| 최대 커넥션 수 | 22 | `max_connections=300`의 7% — 커넥션 풀 고갈 아님 |
| 커넥션 사용률 | 0.667% | 여유 있음 |
| **최대 락 대기 세션(tuple)** | **17~19** | 커넥션 22개 중 거의 전부가 같은 쿠폰 row 락을 기다리며 대기, 3분간 플래토 지속 |
| 최대 커밋 TPS | 30.6 ops/s | **baseline의 최대 커밋 TPS(30.9 ops/s)와 거의 동일** |

**결론**: VU를 10 → 3,000(300배)으로 올렸는데도 실제 처리량(커밋 TPS)은 baseline과 거의 그대로였다. 커넥션 풀과 DB CPU는 모두 여유가 있었던 반면, 커넥션의 대다수가 같은 row의 `SELECT ... FOR UPDATE` 락을 기다리며 멈춰 있었다. 즉 **처리량 상한을 만드는 건 커넥션 풀도 DB CPU도 아니라 비관적 락(행 락) 자체의 직렬화**다. 3,000명이 동시에 몰리면 절반 가까이가 락 대기열 뒤에서 응답을 못 받고 타임아웃된다.

**주의 — Grafana 히스토그램 P95/P99와의 괴리 (→ #36에서 수정)**: 측정 당시 대시보드 요약 타일의
"최대 P95/P99 지연"은 10s로 표시됐지만, k6가 직접 측정한 값은 p95=59.8s, p99=59.8s였다.
`/metrics`의 지연 히스토그램 버킷이 100~500ms 구간 해상도에 맞춰져 있어 그보다 훨씬 큰 값(수십 초)에
대한 버킷이 없었고, `histogram_quantile`이 가장 큰 유한 버킷 상한으로 뭉개 추정한 것이었다. 버킷에
15/30/60/120s 구간을 추가(#36)한 뒤 3번 절에서 재검증했다.

## 3. scaleout (60 req/s, 11분 지속 — #32)

baseline/spike는 부하가 짧게 끝나 HPA가 반응할 시간이 부족했다. `scaleout.js`는 `ramping-arrival-rate`로
초당 요청 수(baseline/spike에서 확인한 커밋 TPS 상한 ~30 ops/s의 2배인 60 req/s)를 8분간 고정해서,
그 시간 동안 파드 수·락 대기·처리량이 어떻게 같이 움직이는지 관찰했다. (이 결과는 #36 수정 이후 재실행한
값이다 — 첫 실행에서는 Grafana P95/P99가 위와 같은 이유로 10s에 눌려 있었다.)

```
총 요청 수: 21223
RPS (평균): 30.75
지연 시간: avg=48710.5ms / p95=60000.6ms / p99=60002.4ms / max=60397.5ms
네트워크 레벨 실패율: 67.54% (14333건, k6 기본 요청 타임아웃 60초 초과)
발급 성공(201): 6889건 (32.46%) / 재고소진(400): 0건 / 중복(409): 0건
```

Grafana에서 관찰된 점 (테스트 구간 기준, #36 수정 후라 P95/P99 수치를 그대로 신뢰 가능):

| 지표 | 값 | 비고 |
|---|---|---|
| Grafana P95 / P99 | 58.5s / 59.7s | k6 실측값(60.0s/60.0s)과 거의 일치 — #36 수정 검증됨 |
| 최대 replicas | **3** | 11분간 지속 압박에도 baseline/spike와 동일하게 3에서 멈춤 |
| 최대 CPU 사용률 | 최대 102%(HPA 평균 기준) / 개별 파드 최대 75.4% | 순간적으로 더 튀었지만 다른 두 테스트와 같은 수준에서 대부분 유지 |
| 최대 커넥션 수 | 33 | `max_connections=300`의 11% — 여전히 여유 |
| **최대 락 대기 세션(tuple)** | 28~29 | 세션 대부분이 락 대기 상태로 8분+ 유지 |
| 최대 커밋 TPS | 32.3 ops/s | **baseline(30.9) · spike(30.6)와 사실상 동일** |

**결론**: 부하 패턴을 완전히 바꿔서(순간 폭주 → 8분간 지속되는 2배 초과 수요) 파드 수·락 대기·처리량의
관계를 다시 봐도 결과는 같았다. 파드는 여전히 3개에서 멈췄고, 커밋 TPS도 여전히 ~30 ops/s였다. DB
패널의 "세션 상태별 수"를 보면 레플리카가 2→3으로 늘어나는 시점에 맞춰 커넥션 수도 한 단계 더
올라갔지만(파드마다 독립적인 커넥션 풀이 하나씩 더 열려서), 그게 처리량 증가로 이어지지는 않았다 —
커넥션이 늘어도 같은 row의 락은 여전히 하나씩만 통과할 수 있기 때문이다.

정리 시 참고: 8분간 쌓인 백엔드 큐가 다 빠지는 데 `run.sh`의 기본 재시도 예산(50초)보다 훨씬 오래
걸렸다 — 자세한 내용과 해결법은 [k6-load-test.md](k6-load-test.md) 7번 참고.

## 4. 종합 결론

| 테스트 | 부하 패턴 | 최대 replicas | 최대 커밋 TPS | 최대 락 대기 세션 |
|---|---|---|---|---|
| baseline | 10 VU, 1분 | 3 | 30.9 ops/s | 8 |
| spike | 3,000명 순간 폭주 | 3 | 30.6 ops/s | 17~19 |
| scaleout | 60 req/s, 8분 지속 | 3 | 32.3 ops/s | 28~29 |

VU 수·요청 패턴·지속 시간을 완전히 다르게 준 세 번의 테스트 모두에서 **처리량 상한이 ~30 ops/s로
수렴**하고 **HPA가 3파드 이상 확장하지 않는다**는 동일한 결과가 나왔다. 이유는 일관된다:

- 커넥션 풀(파드당 10, 최대 33개까지 관찰)과 `max_connections`(300)는 세 테스트 모두 여유가 있었다.
- CPU는 대부분의 요청이 락을 기다리며 블록된 상태(I/O 대기)라 크게 오르지 않았고, 그래서 HPA도
  3파드 이상 늘릴 이유가 없었다.
- 반면 락 대기 세션은 부하가 늘수록(8 → 19 → 29) 계속 늘어났다 — 병목이 정확히 여기에 있다.

**즉 비관적 락(`SELECT ... FOR UPDATE`)에 의한 행 락 직렬화가 이 시스템의 진짜 처리량 상한이며,
파드를 더 늘리는 것(수평 확장)으로는 해결되지 않는다.** 파드가 늘어도 각 파드는 결국 같은 row의
락 하나를 놓고 순서를 기다릴 뿐이다.
