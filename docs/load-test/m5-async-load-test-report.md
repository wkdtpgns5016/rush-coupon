## 1. baseline (10 VU, 1분)

```
총 요청 수: 24,211 (k6 기준)
RPS (k6 평균, 공식 수치): 401.31
API 응답 지연: avg=20.5ms / p95=76.4ms / p99=106.8ms / max=335.1ms
네트워크 레벨 실패율: 0.00%
발급 접수 성공(202): 24,210건 (100.00%)
종단 지연(큐 적재→Worker 저장 완료): avg=18.8ms / p50=-4.8ms(측정 정밀도 노이즈) / p95=217.5ms / p99=343.5ms / max=956.3ms
```

**M3와 같은 10 VU인데 RPS가 27.6 → 401.31로 14배 뛰었다.** 버그가 아니라 k6 `ramping-vus`가 closed-loop 방식이라서다 — M3는 응답이 평균 300ms 걸려 VU 하나가 초당 ~3번밖에 못 돌았지만, M5는 응답이 평균 20ms라 같은 VU가 훨씬 더 자주 돈다. **같은 VU 수가 같은 부하를 의미하지 않는다**는 게 M3 vs M5 비교의 첫 번째 방법론적 주의점이다.

Grafana에서 관찰된 점:
- **HPA가 처음으로 상한(10)까지 확장**: 10 VU짜리 baseline만으로 파드 1개가 CPU 208%(request 대비)까지 튀면서 1분 안에 replicas가 2→10까지 올라갔다. M3는 baseline에서 3파드까지만 갔었다(그마저도 락 대기로 인한 게 아니라 CPU request가 낮게 잡혀 있어서).
- Prometheus 히스토그램 기준 P50/P95/P99(3.99/47.1/70.1ms)가 k6 실측값과 비교적 일치 — baseline은 부하가 1분 가까이 지속돼서 Prometheus `rate(...[1m])`의 윈도우 희석 문제가 크지 않다(spike 절 참고).
- RabbitMQ 큐 길이는 최대 89건까지 쌓였다가 완전히 배출됨. DLQ 0.

## 2. spike (3,000 VU, 각 1회 요청)

```
총 요청 수: 3,001
RPS (k6 평균, 공식 수치): 681.06
API 응답 지연: avg=1,463.3ms / p95=3,371.1ms / p99=3,522.7ms / max=3,755.3ms
네트워크 레벨 실패율: 0.00%
발급 접수 성공(202): 3,000건 (99.97%)
종단 지연: avg=137.2ms / p50=18.5ms / p95=556.8ms / p99=596.8ms / max=961.0ms
```

**M3 대비 가장 극적인 반전.**

| 지표 | M3 spike | M5 spike |
|---|---|---|
| 성공률 | 54.85% (1,646/3,001) | **99.97% (3,000/3,001)** |
| 네트워크 실패(타임아웃) | 45.12% | **0.00%** |
| 소요 시간 | 3,000 VU가 60초 타임아웃까지 끌려감 | **4.4초 만에 3,000/3,000 완료** |
| 평균 지연 | 44,042ms | 1,463ms |
| p99 지연 | 59,822ms | 3,522.7ms |

3,000명이 거의 동시에 몰렸는데 실패 0건, DLQ 0건, 4.4초 만에 다 처리됐다. M3가 보여준 "선착순 몰림 시 절반이 타임아웃"이라는 실패 모드 자체가 사라졌다.

**종단 지연(137~961ms)이 API 응답 지연(1,463~3,755ms)보다 빠르게 나온 것도 정상이다** — `requestedAt`은 Valkey 판정 통과 직후(HTTP 응답을 실제로 클라이언트에 흘려보내기 전)에 찍히는 시점이라, 3,000개 동시 연결이 이벤트 루프에서 응답을 순서대로 흘려보내는 시간은 API 응답 지연에는 포함되지만 종단 지연 계산에는 안 잡힌다. 즉 "판정+발행"은 이미 빨리 끝났고, 느려진 건 HTTP 응답 자체를 3,000개 소켓에 써내려가는 부분이다.

**측정상 주의 — Grafana 패널은 이 시나리오에서 신뢰할 수 없다.** "테스트 요약"이 평균 RPS 4.23 / 최대 RPS 69.6 / 최대 P99 427ms로 나왔지만 k6 실측은 RPS 681 / p99 3,522.7ms다. Prometheus의 `rate(...[1m])`가 4.4초짜리 순간 폭발을 60초 윈도우로 나눠버려서(3,000÷60≈50) 처리량과 분위수 모두 크게 과소평가된다. **spike처럼 수 초 안에 끝나는 시나리오는 k6 자체 리포트를 공식 수치로 쓴다.**

HPA는 3파드까지만 갔는데(M3와 같은 숫자), 이번엔 부하 자체가 4.4초 만에 끝나버려서 HPA가 반응할 시간이 없었을 뿐이다(min=2, max=10 그대로).

## 3. scaleout — M3와 동일 조건 (60 req/s, 11분)

M3와 정확히 같은 설정(`SCALEOUT_RATE=60`, 기본값)으로 재실행해 apples-to-apples 비교를 확보했다.

```
총 요청 수: 34,200 / 목표 34,200 (100% 완주 — M3는 21,223건으로 목표의 약 55%만 소화)
RPS (k6 평균): 51.90
API 응답 지연: avg=20.7ms / p95=85.5ms / p99=114.7ms / max=223.0ms
네트워크 레벨 실패율: 0.00%
발급 접수 성공(202): 34,199건 (100.00%)
종단 지연: avg=215.0ms / p50=214.5ms / p95=450.3ms / p99=483.4ms / max=977.2ms
```

| 지표 | M3 scaleout (60rps) | M5 scaleout (60rps) |
|---|---|---|
| 목표 대비 실제 처리 | 21,223 / ~39,600 (55%, VU가 이전 요청에 묶여 드롭) | **34,200 / 34,200 (100%, 드롭 없음)** |
| 성공률 | 32.46% | **100.00%** |
| 네트워크 실패(타임아웃) | 67.54% | **0.00%** |
| API 응답 지연 | avg 48.7초 / p99 60.0초 | **avg 20.7ms / p99 114.7ms** |
| 최대 replicas | 3 | **2 (아예 안 늘어남)** |

**가장 흥미로운 포인트: HPA가 이번엔 전혀 반응하지 않았다.** replica가 처음부터 끝까지 2(최소값)에 고정됐다 — CPU가 최대 46%(목표 70% 미만)라 스케일업 자체가 필요 없었다. M3는 이 부하로 3대까지 (억지로) 늘려도 실패율이 67%였는데, M5는 최소 구성(2대)만으로 11분간 34,200건을 무결점으로 처리했다. **M3를 무너뜨린 부하가 M5 입장에선 오토스케일링을 켤 필요조차 없는 수준**이라는 뜻이다.

종단 지연(avg 215ms)도 앞뒤가 맞는다 — 60 req/s는 배치(50건)를 순간적으로 채우기엔 느린 속도라 대부분 메시지가 500ms 플러시 타이머를 기다리게 되고, 그 절반 정도(~250ms) 대기가 평균에 반영됐다.

## 4. scaleout — HPA 선형 확장성 검증 (500 req/s, 11분)

60 req/s는 M5에게 트리비얼한 수준이라(위 3번 참고) HPA 확장 곡선 자체를 볼 수 없었다. 이슈 #47의 "HPA 선형 확장성 검증" 목표에 맞춰, baseline에서 관찰된 실제 처리 능력(~400 RPS)을 근거로 목표 요청률을 500 req/s로 올려 별도 실행했다. M3에는 이 조건의 비교 대상이 없으므로 M5 단독 확장성 검증으로 다룬다. 총 두 번 실행했다.

### 4-1. 1차 실행 (15:05) — 일시적 지연 급증 관찰

```
총 요청 수: 257,458 / 목표 285,000 (90%)
RPS (k6 평균): 389.98
API 응답 지연: avg=143.1ms / p95=143.7ms / p99=2,876.6ms / max=33,993.9ms
네트워크 레벨 실패율: 0.01% (31건, dial/request timeout)
발급 접수 성공(202): 257,426건 (99.99%) / 예상치 못한 응답 31건
종단 지연: avg=416.7ms / p50=110.2ms / p95=397.6ms / p99=12,461.0ms / max=58,946.1ms
```

HOLD 구간 중반(15:11~15:13경) RPS가 500→250대로 잠깐 꺼졌다가 회복하는 구간이 있었고, 그 시간대에 RabbitMQ 큐가 320건까지 쌓였다. 31건의 연결 타임아웃과 API/종단 지연의 긴 꼬리(max 34~59초)가 이 구간에서 나왔다.

**원인은 서버 사이드에서 확인되지 않았다.** 점검한 항목:
- `kubectl get events`: 해당 시간대(HOLD 8분 구간 전체)에 파드 재시작·재스케줄·HPA 이벤트가 **전혀 없음** — replicas 10대가 그 구간 내내 안정적으로 떠 있었다.
- CPU 쓰로틀링 비율: 전체 구간 최대 0.5% 미만 — CPU 사용률이 request 대비 127%까지 올랐지만 실제 쓰로틀링(limit 초과)으로 이어지지는 않았다.
- 파드 네트워크 송수신(kb/s): 그 시간대에 낮아졌지만 RPS 하락과 거의 비례한 수준이라(원인이 아니라 결과로 해석), 절대적 크기(수백 KB/s)도 병목이라 보기엔 너무 작다.

즉 CPU/파드/네트워크 어느 것도 원인으로 확정되지 않았다. 클라이언트(k6 실행 머신)-클러스터 간 네트워크 경로(Tailscale) 쪽 일시적 문제로 추정되나 확정하지는 못했다.

### 4-2. 2차 실행 (15:36) — 재현성 확인

동일 조건으로 재실행한 결과 1차의 지연 급증이 **재현되지 않았다**:

```
총 요청 수: 285,000 / 목표 285,000 (100% 완주)
RPS (k6 평균): 431.66
API 응답 지연: avg=36.3ms / p95=111.4ms / p99=152.5ms / max=421.6ms
네트워크 레벨 실패율: 0.00%
발급 접수 성공(202): 284,999건 (100.00%)
종단 지연: avg=69.3ms / p50=55.8ms / p95=206.3ms / p99=328.4ms / max=532.7ms
```

| 지표 | 1차 (15:05) | 2차 (15:36) |
|---|---|---|
| 목표 대비 완주 | 257,458 / 285,000 (90%) | **285,000 / 285,000 (100%)** |
| 성공률 | 99.99% | **100.00%** |
| 네트워크 실패 | 0.01% (31건) | **0.00%** |
| API 응답 max | 33,993.9ms | **421.6ms** |
| 종단 지연 max | 58,946.1ms | **532.7ms** |
| 최대 replicas | 10 | 9 |
| 최대 CPU | 127% | 121% |

동일 조건에서 재현되지 않았다는 것은, 1차의 지연 급증이 아키텍처의 구조적 한계가 아니라 일회성 잡음이었을 가능성이 높다는 뜻이다. **DLQ는 두 실행 모두 0건** — 1차의 지연이 컸던 요청들도 결국 전부 정상 처리됐고 영구 유실은 없었다.

두 실행 모두 replicas가 9~10(상한 10에 근접)까지 올라갔고 CPU도 121~127%까지 튀었다 — **500 req/s는 현재 HPA 설정(max=10)의 실질적 한계에 근접한 수준**이라는 뜻이다. 60 req/s(3번)에서는 최소 구성(2대)으로도 여유 있었던 것과 대조적이다.

## 5. Worker는 시종일관 고정 2대였다

이번 테스트 전체에서 Worker(`k8s/backend/base/worker/deployment.yaml`)는 오토스케일링이 없고 `replicas: 2` 고정이다(KEDA 기반 큐 길이 오토스케일링은 배포 시점에 범위 밖으로 보류됨). 그럼에도 baseline(큐 최대 89건), spike(순간 3,000건 유입에도 즉시 배출), scaleout 60rps(최대 21건), scaleout 500rps(최대 100~320건) **전 시나리오에서 큐가 매번 완전히 배출됐고 DLQ는 단 한 번도 쌓이지 않았다.** 지금 테스트한 부하 범위 안에서는 고정 2대로 충분했다는 뜻이며, 이보다 훨씬 크거나 오래 지속되는 부하에서 Worker 자체가 병목이 될 가능성은 이번 테스트로는 확인되지 않았다(향후 KEDA 도입 검토 대상).

### 6-1. 수치로 본 개선폭

성공률(%p 차이)과 API 응답 지연(감소율/배수)을 M3 대비로 정리했다. **M3 리포트에 p50이 기록되어 있지 않아 avg/p95/p99/max만 비교한다** — M5 쪽 p50은 개별 절(1~4번)의 종단 지연 표에서 별도로 확인할 수 있다.

**성공률**

| 시나리오 | M3 | M5 | 차이 |
|---|---|---|---|
| baseline (10 VU) | 99.94% | 100.00% | +0.06%p |

baseline은 애초에 M3도 락 경합이 크지 않았던 구간이라 개선폭이 상대적으로 작다(4.6~14.6배). spike/scaleout처럼 M3가 60초 타임아웃 벽에 막혀 있던 시나리오일수록 개선폭이 기하급수적으로 커진다 — 특히 scaleout(60rps)은 M3가 사실상 거의 모든 요청을 타임아웃까지 끌고 갔기 때문에 500~2,300배라는 수치가 나오지만, 이는 "M5가 엄청나게 빠르다"기보다 "M3가 그 부하에서 완전히 막혀 있었다"는 걸 반대로 보여주는 숫자로 읽는 게 더 정확하다.

M3(비관적 락)에서 확인됐던 "~30 ops/s에서 처리량이 막히고, 부하가 늘수록 락 대기 세션과 실패율만 늘어난다"는 근본적 한계는 M5(Valkey+RabbitMQ 비동기 아키텍처)에서 **완전히 해소됐다**. 같은 조건(baseline/spike/scaleout 60rps)에서 M3를 무너뜨렸던 부하가 M5에서는 평균 응답 20~40ms대, 성공률 100%에 가깝게 처리됐다.

병목은 사라진 게 아니라 **자리를 옮겼다** — DB 행 락 직렬화 대신, 이제는 API 파드의 HPA 상한(max=10)과 그 CPU 용량이 실질적 한계선이다. 60 req/s에서는 최소 구성(2대)으로도 여유가 있었지만, 500 req/s에서는 레플리카가 9~10(상한 근접)까지 올라가고 CPU가 121~127%까지 튀는 것을 확인했다 — 이 지점이 M5 아키텍처의 "다음 병목 후보"이며, 더 큰 트래픽을 감당하려면 HPA `maxReplicas` 상향이나 파드 리소스 조정이 필요할 수 있다는 것이 이번 검증의 결론이다.

Worker(고정 2대)는 테스트한 모든 부하 범위에서 큐를 문제없이 배출했고 DLQ 유입도 없었다 — 비동기 영속화 계층은 이번 부하 수준에서 병목으로 작용하지 않았다.
